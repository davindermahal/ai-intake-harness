## Bugs found

### 1. [CRITICAL] `set -e` swallows `ai_run_planning`'s error path entirely — kills the whole poller process on any planning failure

**`intake-poll.sh:462`** (`dispatch_planning`):
```sh
ai_run_planning "$key" "$branch" "$ctx" "$dec" "$wt"; rc=$?
```
followed by explicit handling at lines 463–471 (log, remove the ephemeral worktree, `return 0` to
skip just this ticket). That handling is **unreachable**: under `set -euo pipefail` (line 106), a
bare command followed by `; rc=$?` is *not* exempt from `-e` — bash aborts the entire script the
instant `ai_run_planning` returns non-zero, before `rc=$?` ever runs. Verified directly:
```
$ bash -c 'set -euo pipefail; f(){ return 1; }; f; rc=$?; echo "reached rc=$rc"'
# (no output — "reached" never prints, exit code 1)
```
`ai_run_planning` (`lib/ai/claude.sh:52`) wraps `timeout "$CLAUDE_TIMEOUT" "$CLAUDE_BIN" -p ...` —
an ordinary failure mode (900s default timeout, API error, auth failure) returns non-zero.

**Failure scenario**: one planning LLM call times out or errors. The **entire poller process
dies** at line 462 — not just that ticket. Since `dispatch_planning` runs inside `process_queue`
under `--mode both`'s sequential pass, the implementation-queue dispatch and watchdog sweep for
this cycle **never run at all**, silently, until the next cron tick. `inflight_mark "$key"`
(already called at line 444) is never cleared by the (unreached) cleanup, locking that ticket out
of re-pickup for `INFLIGHT_STALE_SECONDS` (1800s). The ephemeral planning worktree at `$wt`
(created lines 449–452) is never `git worktree remove`d — it leaks on disk, accumulating one stale
sibling directory per timeout.

Notably, the author was clearly aware of this exact hazard elsewhere: `post_comment()`
(`intake-poll.sh:163–172`) has a long comment explaining why `tracker_add_comment` must be
`||`-guarded for precisely this reason ("a raw call left unguarded would abort THIS ENTIRE POLL
RUN on any failure, stranding whatever ticket was mid-flight"). The same guard was never applied
to `ai_run_planning` — the dead-code path at 463–471 was presumably written and only ever
exercised against a *successful* `ai_run_planning`, never a real failure.

**Suggested fix**: `rc=0; ai_run_planning "$key" "$branch" "$ctx" "$dec" "$wt" || rc=$?` — the
`||` form is exempt from `-e`, so the existing `if [ "$rc" -ne 0 ]` block then runs as designed.

### 2. [HIGH] A failed post-launch status transition can double-launch an AI worker into the same worktree

**`intake-poll.sh:602`** (`dispatch_implementation`):
```sh
tracker_transition "$key" in-progress && inflight_clear "$key"
```
No `else`. If this one REST call fails (transient Jira error, or a misconfigured/renamed "In
Progress" status), `inflight_clear` never runs and nothing is escalated or logged beyond the
poll log — the ticket's tracker status is still "Ready for Implementation", so `tracker_search
implementation` keeps returning it every poll.

`INFLIGHT_STALE_SECONDS` (default 1800s / 30 min) is far shorter than the worker's own run budget
(`JIRA_RUN_STALE_SECONDS`, default 14400s / 4h), so the stale in-flight marker gets reclaimed while
the first worker is still legitimately running its build/verify. The ticket is then re-dispatched:
`launch_implementation_worker` → `worktree-go.sh` sees the worktree dir already exists → auto-sets
`RESUME=1` → launches a **second** detached AI worker into the **same worktree**.

Makes it worse: **`worktree-go.sh:231`** writes `RUNNING_PIDFILE` unconditionally, with no check
for an already-live PID before overwrite:
```sh
RUNNING_PIDFILE="${RUNNING_DIR}/${TICKET:-noticket}.pid"
...
ai_run_implementation "$LOGFILE" "$RUNNING_PIDFILE"
```
The second worker's PID silently clobbers the first's. `reap_running`'s `kill -0` liveness check
now only ever sees the second PID — the first worker becomes an **untracked, unreaped background
process**, still running and still able to write commits/build output into the same worktree the
second worker is concurrently touching.

**Failure scenario**: Jira has a brief 5xx blip right after a worker launches successfully. The
transition call fails once. 30+ minutes later the ticket gets re-dispatched into the same worktree
while the original worker is still mid-build; two AI agents now write to the same git working tree
and the same `.ai/impl-result.json` path concurrently.

**Suggested fix**: add an `else` that escalates (`dispatch_escalate_once`, mirroring the
worktree-provisioning-failure branch two lines below) and does **not** clear the in-flight marker
early — or, more robustly, have `launch_implementation_worker` refuse to launch when
`$RUNNING_DIR/$key.pid` already names a live PID (the same `worker_running` check
`worktree-remove.sh` already has).

### 3. [HIGH] Same missing-else bug in the planning phase → silent infinite retry + duplicate comments

**`intake-poll.sh:523-524`** (`dispatch_planning`):
```sh
questions) tracker_transition "$key" needs-author-input && inflight_clear "$key" ;;
clean)     tracker_transition "$key" plan-review        && inflight_clear "$key" ;;
```
Same pattern, no `else`, and — unlike the AI-provider-failure path (line ~439) or the
no-feature-branch path in `dispatch_implementation` (line ~571) — **no `dispatch_escalate_once`
call exists for this failure**. Worse here because the plan summary comment is posted
*unconditionally, before* the transition attempt (`intake-poll.sh:521`):
```sh
[ -n "$comment" ] && post_comment "$key" "$comment"   # always post the summary (best-effort)
case "$action" in
    ...
```
**Failure scenario**: the "Plan Review" (or "Needs Author Input") status name is misconfigured or
renamed on the tracker side (exactly the class of drift `install.sh --verify`'s live status-mapping
check exists to catch, but only if someone runs `--verify`). Every ~30 minutes, once the in-flight
marker goes stale, the poller reruns the **entire planning pass** — a fresh ephemeral worktree, a
new billed LLM invocation — and reposts the **identical** "plan ready" comment to the ticket.
Forever, with zero human-visible escalation; the only trace is the poll log.

**Suggested fix**: same as #2 — escalate once on transition failure instead of silently retrying
the whole phase from scratch.

### 4. [HIGH] `wt_create_empty_db` has no guard against dropping the shared source database

**`lib/worktree-common.sh:65-71`**:
```sh
# Usage: wt_create_empty_db <db-name> <pg-user> <pg-password>
wt_create_empty_db() {
    local db="$1" user="$2" pass="$3"
    PGPASSWORD="$pass" psql -h localhost -U "$user" -d postgres \
        -c "DROP DATABASE IF EXISTS \"${db}\"" \
        -c "CREATE DATABASE \"${db}\"" > /dev/null
}
```
Its sibling `wt_drop_db` (`lib/worktree-common.sh:169-186`) explicitly documents and enforces two
guards — `$db` must match `${PROJECT_DB_PREFIX}_*` AND must differ from `$source_db` — specifically
"so we can never drop the source DB." `wt_create_empty_db` runs an unconditional
`DROP DATABASE IF EXISTS` + `CREATE DATABASE` on whatever `$db` it's given, with **no prefix check
and no source-DB check at all**. It's called from `worktree-go.sh:137` and `worktree-new.sh:67`
with `$DB_NAME`, a value computed entirely by the (out-of-repo, project-specific)
`project_derive_names` adapter function — this harness's own shared plumbing applies zero
defense-in-depth to that input.

**Failure scenario**: a project adapter's branch→DB-name derivation has an edge case (empty/short
slug, collision on a short ticket key, a bug in a future adapter) that produces a name equal to
`$SOURCE_DB`. `wt_create_empty_db "$SOURCE_DB" ...` silently drops and recreates the shared
dev/main database empty, before `wt_clone_db` even runs — with no confirmation prompt, unlike the
guard its sibling function has.

**Suggested fix**: give `wt_create_empty_db` the same two guards `wt_drop_db` already has (prefix
match + `!= source_db`), refusing and returning non-zero instead of running the `DROP`/`CREATE`.

### 5. [MEDIUM] Stale hardcoded `make jira-plan` in a user-facing Jira comment — target doesn't exist

```
Full plan (..., too large to inline) ... or run `make jira-plan KEY=$key` locally.
```
`jira-plan` is not defined anywhere — not in this repo, not in README's documented Makefile

```makefile
intake-plan:
	@test -n "$(KEY)" || (echo "Usage: make intake-plan KEY=<TICKET-NN>" && exit 1)
```

Confirmed via `grep -rn "jira-plan:"` across the repo — no match anywhere, not even as an alias.

**Suggested fix**: `s/make jira-plan/make intake-plan/` in `intake-poll.sh` at all three
occurrences.

### 6. [MEDIUM] `jira_search_jql` caps at 50 results with no pagination and no truncation warning

**`lib/tracker/jira-common.sh:154-166`**:
```sh
jira_search_jql() {
    local jql="$1" resp
    resp="$(curl -sS "${_JIRA_AUTH_OPTS[@]}" \
        -G "$JIRA_SITE_URL/rest/api/3/search/jql" \
        --data-urlencode "jql=$jql" \
        --data-urlencode "fields=key" \
        --data-urlencode "maxResults=50" \
        ...
```
No loop over `nextPageToken`/`startAt`, and no check of whether the response was actually
truncated. Any queue (`ready-for-planning`, `ready-for-implementation`, `in-progress`) with more
than 50 matching tickets silently drops everything past the 50th-oldest (`ORDER BY created ASC`)
— not stuck forever (they'll surface once the queue drains below 50), but silently invisible to
the poller with zero log line indicating a cap was hit.

**Suggested fix**: loop on `nextPageToken` until exhausted, or at minimum log a warning when
`.issues | length == 50` (cap possibly hit, more may exist).

### 7. [MEDIUM] `flock` is only an external cron-wrapper convention — not enforced inside `intake-poll.sh`

`intake-poll.sh` never calls `flock` itself (only mentions are in comments and the crontab
example in the header). The *only* real double-dispatch guard is the in-flight marker set
(`inflight_mark`/`inflight_active`, `intake-poll.sh:185-197`), which is non-atomic — a plain
`stat` read followed by a separate `date +%s > file` write, no `mkdir`/`O_EXCL`-style locking.
As long as every invocation goes through the documented `flock -n .intake/poll.lock` wrapper
(`scripts/intake-cron.sh`, scaffolded by `install.sh`), this is safe. But there's no in-script
defense-in-depth: a second cron line, a manual concurrent run, or a different scheduler that
skips the flock wrapper can freely double-dispatch the same ticket, since two processes can both
observe "not in-flight" before either writes the marker.

**Suggested fix**: not urgent given the documented/scaffolded usage always goes through flock, but
worth either enforcing the lock inside `intake-poll.sh` itself (belt-and-suspenders) or at least
noting the assumption more forcefully in the script's own preamble (currently only in a comment).

### 8. [MEDIUM] Unescaped SQL string interpolation in `wt_drop_db` / `wt_create_empty_db`

**`lib/worktree-common.sh:69-70, 181-186`**:
```sh
# wt_create_empty_db
-c "DROP DATABASE IF EXISTS \"${db}\"" \
-c "CREATE DATABASE \"${db}\""

# wt_drop_db
"SELECT 1 FROM pg_database WHERE datname = '${db}'"
...
-c "DROP DATABASE IF EXISTS \"${db}\""
```
`$db` is interpolated directly into the SQL text with no quote-escaping. `wt_drop_db`'s prefix
guard only checks that the name *starts with* `${PROJECT_DB_PREFIX}_` — it does not constrain or
escape the rest of the string. `DB_NAME` is produced entirely by the consumer repo's own
`project_derive_names` (not part of this harness), which README documents with no sanitization
requirement on its output. This repo's own shared plumbing (`lib/worktree-common.sh`) has no
defense-in-depth here: a project adapter that derives a DB name loosely from a branch/ticket name
containing a `"` or `'` could break out of the intended SQL statement.

**Suggested fix**: escape embedded quotes before interpolating, or use `psql -v db=... -c
'DROP DATABASE IF EXISTS :"db"'` (variable substitution with proper identifier quoting) instead of
string-building the SQL by hand.

### 9. [LOW] Watchdog stale-comment check silently misclassifies an unparseable timestamp

`intake-poll.sh`'s `watchdog_stalled_comment_after` converts a Jira comment's `created` timestamp
via `date -d "$created" +%s 2>/dev/null || echo 0`. A parse failure silently becomes epoch `0`,
which can never be `> $launched`, so the function returns exactly the same result as "no comment
posted yet" (case A: safe to auto-restart) — even though the real situation could be case C
("worker already reported a blocker, don't restart"). Low likelihood in practice (GNU `date -d`
handles Jira's ISO-8601 timestamps fine) and there's no diagnostic if it ever does misfire, so a
misclassification would be silent.

**Suggested fix**: log a warning when the parse falls back to 0, so a future format change
(different tracker adapter, Jira API version bump) doesn't fail silently toward the wrong branch.

### 10. [LOW] Planning-phase Claude run has no technical permission/tool restriction

`lib/ai/claude.sh`'s planning-phase launch uses only `--permission-mode acceptEdits` — no
settings/profile file, unlike the implementation phase, which fails closed without one
(`project_permission_profile` required). The stated "never touch Jira/git" boundary during
planning (see the prompt text passed to the AI) rests entirely on prompt instructions, not a
technical control. It's incidentally mitigated: the ephemeral planning worktree
(`intake-poll.sh`'s `dispatch_planning`, plain `git worktree add`) never gets `.env`/`.env.local`
copied in (gitignored, absent from a fresh checkout), so Jira credentials aren't directly reachable
from that cwd — but that's a side effect of file layout, not a designed guard, and it doesn't
constrain other unsupervised shell/tool actions during planning.

## Documentation/code alignment findings

Doc drift doesn't break the harness but will actively mislead anyone reading these files as
current truth, and two items below (#8/#9) mean a consumer implementing the project-adapter
contract purely from README would write functions with the wrong parameter lists.

   call site — `worktree-go.sh:168` — invokes it with 7:

   "$POSTGRES_USER" "$POSTGRES_PASSWORD"`. `repo-root`, `db-name`, `postgres-user`,

2. **`README.md:168` (`project_install_deps <worktree-dir>`)** documents 1 arg. Actual call

   `worktree-new.sh:92` both call `project_migrate "$APP_CONTAINER" "$USER_ID" "$GROUP_ID"` on the
